# تقرير جاهزية العرض التجريبي (Pilot) — نظام ERP مصنع القمة

التاريخ: 2026-11-08 · الفرع: `feat/api-readiness-check` (غير مُدمج، غير مرفوع) · قاعدة العرض: `qemma_pilot_demo` (محلية ومستقلة)

> تصنيف الحالة في هذا التقرير:
> **منفذ ومختبر** = جرى تنفيذه عبر الواجهة في المتصفح على خادم حقيقي وتطابقت الأرصدة · **مختبر عبر الـ API** = عبر الخادم الحقيقي دون المتصفح · **جزئي** = يعمل مع قيود مذكورة · **غير متاح** = لا يُعرض.

## 1. ما كان منجزاً قبل هذه المهمة

- إصدار «سلامة التشغيل» (ترحيل 0017): الخزينة نقطة الاعتماد الوحيدة، فصل المنشئ عن المعتمد، استلام جزئي لفواتير الموردين مع خصم لكل بند، استلام منتج تام لكل مقاس، تسوية خامات الورشة، إغلاق الأمر، تحصيلات معلقة حتى الاعتماد، دفاتر نقدية وقيود غير قابلة للتعديل.
- اختبار دورة كاملة على مستوى الـ API (`tests/test_operational_cycle_e2e.py`) ناجح.
- **لم توجد في المستودع** ملفات «طبقة الدعم الهندسي بالذكاء الاصطناعي» المشار إليها (خريطة المشروع/تقرير الإكمال). اعتمدتُ بدلاً منها على: `docs/QEMA_FULL_CODEBASE_ENGINEERING_AUDIT_2026-11-08_AR.md` (أرشيفي)، `docs/API_CONTRACT_CHANGES_2026-11-08.md`، `docs/KNOWN_LIMITATIONS_AR.md`.

## 2. ما أُعيد استخدامه

كل منطق الأعمال القائم دون تغيير في القواعد: دفتر المخزن، أقفال منع الرصيد السالب، الخزينة والاعتماد، الصلاحيات الأربع. لم تُضف أدوار ولا صلاحيات جديدة؛ كل نقطة جديدة تستخدم صلاحية موجودة.

## 4. ما أُصلح (مرتب حسب الخطورة)

### حرج
1. **CORS يرفض ترويسة `Idempotency-Key`** ← كانت كل عمليات الإنتاج المحمية من التكرار تفشل من المتصفح (استلام الورشة، استلام المنتج التام، التسوية، الإغلاق) عند فصل الواجهة عن الخادم. أُضيفت الترويسة + اختبار.
2. **شاشة فواتير الشراء تحسب أرقامها بنفسها** وتخالف الخادم: تجاهل الخصم (49,000 بدل 48,500)، الاستلام الجزئي يظهر «تم الاستلام» مع استحقاق 2,000 بدل 1,200، ولا طريقة لاستلام الباقي. أعيدت كتابتها لتعرض أرقام الخادم كما هي، مع خصم لكل بند، استلام على دفعات بعمود «المتبقي»، وسقف السداد = المستحق الفعلي.
3. **رسائل مالية مضللة**: زر «سداد واعتماد وترحيل الدفعة فوراً» ونموذج التحصيل «يُعتمد ويُرحّل فوراً» بينما الحقيقة أنها معلقة حتى اعتماد شخص آخر. صُححت، وأُزيل زر الاعتماد من شاشة الموردين (الاعتماد من الخزينة فقط).
4. **أوامر ونماذج وهمية عند فشل الاتصال**: `fetchProducts/fetchOrders/fetchTemplates/fetchWarehouses` كانت تعيد بيانات تجريبية ثابتة عند أي خطأ، فقد ينشئ الموظف أمراً على موديل غير موجود. أُزيلت؛ يظهر الخطأ الحقيقي.
5. **تقرير المخزون يعرض عجز النقل كرصيد في «مخزن عام» غير موجود**. أصبح التقرير يعرض أرصدة المخازن الثلاثة فقط، والعجز في قائمة مستقلة `transfer_discrepancies`.

### مرتفع
6. 7 نقاط اعتماد/تقديم الأصناف تعيد خطأ 500 على الخادم الحقيقي (تحميل كسول للعلاقات؛ لم تكشفه الاختبارات لأنها تشارك جلسة واحدة). + اختبار بجلسة مستقلة لكل طلب.
7. `/production/catalog-items` يعرض كل الأصناف «مسودة» → قائمة الخامات في الشراء فارغة دائماً.
8. نموذج استلام الخامات بالورشة يبدأ بأصفار وفارق أحمر -140 بدل الكمية المنصرفة.
9. أوامر متعددة المقاسات تظهر بمقاس واحد في القائمة والتفاصيل؛ قائمة إضافة الخامات تعرض منتجات تامة.
10. لوحة التشغيل: عدد «الأوامر النشطة» بثلاث قيم مختلفة في نفس الصفحة (1 / 3 / 0) بسبب اسم حالة خاطئ (`in_progress` بدل `in_production`) واحتساب المغلق.
11. رسالة التراجع عن المراحل «حالة المرحلة تغيرت» عند محاولة إكمال مرحلة لم تبدأ → رسائل محددة.

### سهولة الاستخدام
- القائمة مرتبة حسب دورة العمل: صندوق المهام ← المشتريات ← المخازن ← أوامر التشغيل ← المبيعات ← المالية ← البيانات الأساسية؛ نفس الأسماء لكل الأدوار.
- إزالة شريطي «LOCAL DEV MODE/Supabase» المتناقضين، شارة «الوردية الصباحية» الوهمية، وزر «كل المخازن» غير العامل؛ شريط واحد يميز بيانات العرض (DEMO / «تجريبي»).
- شاشة رفض الصلاحية بالعربية دون «403 Forbidden» أو رموز صلاحيات.
- أسماء المستخدمين بدلاً من المعرّفات الطويلة في الخزينة وصندوق المهام.
- طلب العميل: عرض إجمالي الأصناف والخصم وصافي الطلب أثناء الإدخال؛ «طلب جديد» بدل «معاملة»؛ ملخص العميل يعرض قيمة المسلَّم، المحصّل المعتمد، التحصيلات المعلقة، والمستحق الآن.
- أوامر التشغيل: «التالي:» لكل أمر مع صاحب الدور، واستبدال لوحة «افتراضات اجتماع المصنع» القديمة بدليل خطوات صحيح.
- المواسم بالعربية، وتسمية «مدير الإنتاج» الخاطئة في نافذة الدخول.

## 6. بيانات العرض (DEMO-PILOT)

كل السجلات بكود `DEMO-` وأسماء تنتهي بـ «(تجريبي)»، وتُبنى عبر الـ API نفسه:
- **3 موردين** (أقمشة، مستلزمات خياطة، تعبئة) + 3 فواتير: مستلمة ومسددة جزئياً، مستلمة غير مسددة، **مستلمة جزئياً** (لعرض استلام الباقي).
- **3 عملاء**: طلب مسلَّم جزئياً ومحصّل جزئياً، طلب لم يُسلَّم مع **عربون معلق** في الخزينة (لعرض الاعتماد)، وعميل بلا طلبات (لإنشاء طلب أمام المصنع).
- **8 خامات** معتمدة، **7 موديلات** بمقاسات ومواسم (منها موديل أُضيف عبر الشاشة الجديدة).
- **3 أوامر تشغيل**: مغلق كامل الدورة (3 مقاسات، قطعة مرفوضة، عجز نقل، مرتجع وهالك)، جارٍ في التقفيل، ومسودة جاهزة للصرف أمام المصنع.
- رصيد خزنة افتتاحي 150,000 (مستند قبض معتمد بشخص آخر).

## 7. ما يُعرض بأمان

المشتريات والاستلام الجزئي والسداد · الخزينة والاعتماد بشخصين · البيانات الأساسية · دورة أمر التشغيل كاملة · طلبات العملاء والتسليم والتحصيل · صندوق المهام · لوحة التشغيل · تقارير المديونيات والمستحقات وكشوف الحساب والمخزون.

## 8. ما لا يُعرض بعد (أو يُعرض مع التنبيه)

| البند | السبب |
|---|---|
| الرواتب | لا توجد معادلات معتمدة من المصنع؛ القيم يدوية فقط |
| الميزانية وقائمة الدخل وميزان المراجعة | دليل الحسابات بلا أرصدة افتتاحية وتصنيف المصروفات بالكلمات (انظر القيود المعروفة) |
| تكلفة المنتج | خامات فقط، دون أجور أو غير مباشرة — قرار معلق |
| مرتجعات العملاء والجرد والعُهد | سليمة في الاختبارات الآلية لكنها **لم تُجرَّب بالمتصفح** في هذه الجولة |
| إلغاء/عكس مستند معتمد | غير موجود (قرار معلق) |
| إدارة المستخدمين والأدوار من الواجهة | غير موجودة؛ بأمر SQL |
| الماكينات والمعدات | شاشة «قيد التطوير» |

## 9. ملاحظات وقرارات تحتاج المصنع/المطور

- أمين المخزن يملك `suppliers:manage` فيستطيع **طلب** سداد مورد عبر الـ API (الواجهة تخفيه عنه، والاعتماد يبقى في الخزينة). يحتاج قراراً هل تُسحب منه.
- استلام المنتج التام: المقاس الذي به قطع مرفوضة يبقى «متبقي 1» ويُقترح 1 للاستلام التالي؛ يُغلق الأمر بذكر سبب النقص. قد يحتاج المصنع قاعدة أوضح.
- نموذج طلب العميل لا يعرض الرصيد المتاح لكل مقاس (يظهر في شاشة «تسليم الطلبات»).
- اسم المورد/الموديل في الفواتير والطلبات السابقة يُقرأ من السجل الحالي؛ المبالغ والكميات المعتمدة لا تتغير.

## 10. خطوات التشغيل يوم العرض

```powershell
cd apps/api
.\.venv\Scripts\python scripts\reset_pilot_demo_db.py --yes   # قاعدة عرض نظيفة
.\.venv\Scripts\python scripts\run_pilot_api.py               # نافذة 1: الـ API على 8010

```
```powershell
cd apps/web
$env:VITE_API_BASE_URL="http://localhost:8010"; npm run dev -- --port 5180   # نافذة 2
```
ثم افتح http://localhost:5180 ← «تسجيل الدخول» ← اختر الدور. للتبديل بين الأدوار: «إدارة الجلسة» ← «تبديل الدور».

**قبل أي نشر حقيقي**: بيئة `production` تُعطل الدخول المحلي؛ يجب تهيئة Supabase وإسناد الأدوار (دليل التشغيل §4)، وعدم استخدام قاعدة العرض.

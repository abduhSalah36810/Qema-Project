**ثوابت محلية تحتاج استخراجًا:** `STAGE_TITLES_AR`, `STAGE_SEQUENCE` (القص→التشطيب→الكبسولة→الكي→التعبئة), `STAGE_STATUS_AR`, `DELAY_REASONS_AR`, `ORDER_STATUS_AR`, `RETURN_CONDITION_LABELS`, `FG_RECEIPT_STATUSES`, `RECONCILIATION_STATUSES`, `ROLLBACK_STATUSES`, دوال `parseApiError`/`stageLockReason`/`refreshAfterSuccess`/`fmtQty`.

**التبويبات ومربوطاتها:**

1. **items — الموديلات والمقاسات** (1061–1108): جدول البنود (موديل/مقاس/مستهدف/مستلم سليم/نوع التصنيع: براند المصنع أم تصنيع لعميل/مواصفات القماش) + مكون محلي `OrderBomSnapshot` (169–260): نسخة المستلزمات المحفوظة وقت الإنشاء + جدول إجمالي الاحتياج مقابل المخطط/المنصرف/المستلم. لا API إضافي.
2. **materials — الخامات: الصرف والاستلام** (1111–1334):
   - شريط إجراءات متغير بالحالة: الخطوة 1 صرف (`draft` + `canDispatch`)، الخطوة 2 تأكيد استلام الورشة (`materials_dispatched` + `canReceiveWip` مع فصل المسؤول عن الصرف `dispatchedByMe`)، ثم صندوق «✓ مستلمة».
   - نموذج إضافة/حذف خامة في المسودة فقط (`canManageMaterials`, `addOrderMaterialApi`/`removeOrderMaterialApi`, بنود المستلزمات المحفوظة «ثابتة»).
   - جدول الخامات: مخطط/منصرف/مستلم/فارق/حالة + إدخال استلام لكل سطر (من 0 إلى المنصرف) + سبب الفارق + عمود المصدر (مستلزمات/يدوي).
   - `ExtraIssuePanel` بعد الصرف (صرف إضافي/مرتجعات، بصلاحيتيه).
3. **stages — مراحل التصنيع** (1338–1573): بطاقات المراحل الخمس بقاعدة التتابع الإلزامي، بدء/إكمال/تخطي (بسبب)/إعادة فتح (بسبب ≥3 أحرف)/تعديل المدة المعيارية، أسباب التأخير الفني (`material_shortage`…)، ملاحظات، لقطة التوقيت (متوقع/فعلي/تقويمي، تقديري أم معتمد)، سجل التغييرات الموثقة، وسم «اختناق تشغيلي». الصلاحية `production:stages:manage`؛ القفل بالحالة عبر `stageLockReason` (الخادم يرفض خارج `in_production`).
4. **defects — العيوب والهالك** (1575–1615): نموذج تسجيل عيب (مرحلة/كمية/مسؤول/وصف/إجراء/تكلفة وصفية) + قائمة العيوب مع تحديث حالة الإصلاح. API: `fetchOrderDefects`/`reportOrderDefect`/`updateOrderDefect`.
5. **fg_receipt — استلام المنتج التام** (1618–1735): جدول لكل بند (الملكية: براند المصنع أو تصنيع خاص للعميل/المستهدف/المستلم سليمًا/المرفوض/المتبقي) + إدخال سليم الآن/مرفوض الآن + ملاحظات فحص الجودة. `receiveFinishedGoodsApi` بمفتاح Idempotency؛ متاح في `in_production`/`manufacturing_completed`؛ الصلاحية `warehouse:finished_goods:receive`.
6. **wip — التسوية والمرتجعات والإغلاق** (1738–1991): **أكثر تبويب مزدحم — 4 وظائف متمايزة:**
   - قسم مطالبات عجز الاستلام (T2): `DiscrepancyClaimsSection` + تحميل `fetchOrderDiscrepancyClaims` + `DiscrepancyClaimDetailModal` للحسم (3 قرارات، Maker-Checker).
   - نموذج تسوية خامات الورشة: `fetchOrderWipSummary` → جدول (منصرف/مستلم/رصيد/مستهلك/مرتجع/تالف/حالة المرتجع/المتبقي) قيود الخادم (المجموع ≤ الرصيد، ملاحظة إلزامية لمرتجع غير سليم). `reconcileOrderMaterialsApi` بمفتاح Idempotency.
   - `WorkshopReturnsPanel` (مرتجعات الورشة: فحص واستلام أمين المخزن + قرار عجز/رفض للإنتاج أو المدير العام).
   - قسم إغلاق الأمر: ملخص (مستلم من مستهدف، فروقات)، `blocking_reasons` من الخادم + `hardCloseBlockers` محسوبة محليًا (مراحل غير مكتملة، تحويل بالطريق، مرتجع بانتظار قرار، رصيد ورشة ≠ 0)، إقرار اعتماد الفروقات، سبب العجز الإنتاجي، ملاحظات، زر الإغلاق النهائي (`production:orders:close`).
7. **costing — التكاليف والهالك** (1994–2209): بطاقات التكاليف (خامات/أجور/غير مباشرة/إجمالي/تكلفة القطعة)، نموذج معايير الأجور (`piece_based`/`time_based` + معدل + ساعات + أساس توزيع الأعباء + المعدل) عبر `calculateOrderCosts`، ونموذج الاستهلاك الفعلي/الهالك/المرتجع لكل خامة مع أعمدة **الملكية (العميل/المصنع)** و**المعاملة التجارية** ووسم تجاوز الهالك `excess_waste_qty` عبر `logOrderMaterialConsumption`.

**دورة تحديث موحدة:** كل عملية ناجحة تمر عبر `refreshAfterSuccess` = إعادة جلب الأمر `fetchProductionOrderById` + رسالة نجاح، وعند فشل التحديث: `hasPendingRefresh` + زر مزامنة. يجب الحفاظ على هذا العقد في الصفحة الجديدة.

### 1.3 الصلاحيات داخل الشاشات (RBAC الحالي)

| الإجراء | الصلاحية | ملاحظات |
|---|---|---|
| صرف الخامات | `warehouse:dispatch` | |
| تأكيد استلام الورشة | `production:wip:receive` + ليس من صرفها (`dispatchedByMe`) | فصل مسؤوليات مؤكد خادميًا أيضًا |
| تحديث/تخطي/تراجع المراحل + تعديل المدة | `production:stages:manage` | مقفول خارج `in_production` |
| تسجيل العيوب + إضافة/حذف خامات المسودة + التسوية | `production:orders:manage` | |
| استلام المنتج التام | `warehouse:finished_goods:receive` | |
| استلام المرتجعات / قرار عجز المرتجع | `warehouse:returns:receive` / `production:returns:resolve` | مع استبعاد من أثبت/سجل سابقًا |
| حسم مطالبات العجز (T2) | `warehouse:claims:resolve` (WM+GM) | Maker-Checker: المُقدِّم لا يحسم |
| إغلاق الأمر | `production:orders:close` | محجوب بمطالبات معلقة (`pending_claims_count`) |
| ظهور تبويب المراحل | `production:stages:manage` أو `production:orders:close` | |
| التبويب الافتراضي | `nextStep(order, hasPermission, userId).isMine ? next.tab : 'materials'` | عقد `orderWorkflow` |
| أدوات الشريط في الـHub (خامات العملاء/التقويم) | `production:orders:manage` (T1) | |
| Demand Pool: قراءة / إنشاء | أي-من (`production:orders:view` \| `customers:orders:view`) / `production:orders:create` | T3 |

**حالة التنقل (App.tsx):**
- `PRODUCTION_NAV` (PM): أوامر التشغيل → سلة طلبات العملاء (التجميع) → مطالبات فروقات الاستلام → (مجموعة المبيعات والتسليم…).
- `GENERAL_NAV` (GM): نفس المداخل + أرصدة الخامات.
- `WAREHOUSE_NAV` (WM): «صرف الخامات واستلام التام» + مطالبات الفروقات.
- `ROUTE_PERMISSIONS`: `batches: production:orders:view`؛ `production-claims`: أي-من (3)؛ `demand-pool`: أي-من (2).
- التنقل حالة `activeNav` + `NavFocus {orderId?, orderTab?}` — **لا router URL**؛ التفاصيل تُفتح كـModal داخل الـHub (`openOrder(order, tab)`).

## القسم 2 — شجرة المكونات والمسارات المقترحة (Proposed Component Tree & Routes)

### 2.1 مبدآن حاكمان للتصميم

1. **عقد التنقل ثابت:** يبقى `OrderDetailTab = 'items'|'materials'|'stages'|'defects'|'fg_receipt'|'wip'` في `@/lib/navigation.ts` كما هو، وتبقى `NavFocus {orderId, orderTab}` واجهة التعميق من صندوق المهام/السلة/المطالبات. الصفحة الجديدة تستقبل نفس المعرّفات وتساويها داخليًا على تبويباتها الستة عبر طبقة تحويل موثقة.
2. **تفكيك قبل إعادة التجميع:** كل منطق الـModal ينتقل كما هو إلى أقسام أولًا (صفر تغيير سلوكي)، ثم تُركَّب الأقسام في صفحة، ثم فقط تُضاف الديناميكية (نظرة عامة + مصفوفة Internal/CMT).

**قرارات تصميمية موثقة (تحتاج اعتمادًا):**
- **D-4.1a:** تبويب costing يُدمج: بطاقات الملخص في «نظرة عامة»، ومعايير الأجور والاستهلاك الفعلي/انحراف الهالك في «الإغلاق» (هي المراجعة النهائية للتكلفة) — أو كاملة في «التسوية». الافتراض المقترح: **الإغلاق**، لأن استهلاك الخامات الفعلي يغذّي قرار الإغلاق.
- **D-4.1b:** مطالبات العجز (T2) تعرض في «الخامات» (موضع الفارق) وتظل أيضًا مرجعًا لحاجز الإغلاق في «الإغلاق» — عرض مزدوج (نفس المكون، بدون تكرار منطق).
- **D-4.1c:** إبقاء فتح التفاصيل **صفحة داخل مسار `batches`** (Hub ← → تفاصيل) في هذه المرحلة؛ تحويلها لمسار URL مستقل يتطلب قرار Router عام (خارج نطاق T4).

### 2.3 شجرة مساحة الإنتاج (Production Workspace Navigation)

```
PRODUCTION_NAV (مساحة مدير الإنتاج)
├── 1. مركز أوامر التشغيل  (batches)         ← ProductionOrdersView المطوّر (Hub + OrderDetailsPage)
├── 2. سلة طلبات العملاء    (demand-pool)     ← DemandPoolView (T3 — جاهزة)
├── 3. الخامات والمطالبات   (production-claims + أرصدة الخامات) ← DiscrepancyClaimsView (T2) + رابط المخازن
├── 4. أرضية التشغيل والمراحل (جديد: عدسة عرض على الـHub، لا Backend)
│     فلاتر: قيد الإنتاج / اختناقات / متأخرة — بطاقات المراحل من بيانات القائمة الحالية
├── 5. المنتج التام         (جديد: عدسة عرض manufacturing_completed/receipt_completed)
└── 6. التقارير والاختناقات (مرجع: BottleneckCalendarModal + مؤشرات T6 لاحقًا)
```

- النقاط 4 و5 **عدسات فلترة** على نفس `fetchOrders` (البيانات تشمل `stage_events` و`is_bottleneck` و`received_quantity`) — صفر تغيير خادمي. تُنفَّذ كتبويبات/فلاتر داخل الـHub أو مساحتين خفيفتين، بحسب اعتمادك.
- **ترحيل تدريجي:** T4.2 ينفّذ 1 (الصفحة الجديدة)؛ نقاط 4/5/6 تُنفَّذ بعد اعتماد T4.2 (نقطة 6 تتقاطع مع T6 المخطط لها أصلًا).

### 2.4 مصفوفة صلاحيات مساحة الإنتاج (من يرى ماذا)

| مساحة | PM (production_manager) | GM (general_manager) | WM (warehouse_keeper) | Finance/أخرى |
|---|---|---|---|---|
| مركز الأوامر | ✅ كامل (إنشاء/إدارة) | ✅ كامل | ✅ محصور بمهامه (صرف/استلام) — إجراءات الإنتاج مخفية | قراءة حسب `production:orders:view` |
| سلة الطلبات | قراءة + إنشاء | قراءة + إنشاء | قراءة (عرض `production:orders:view`) | قراءة عبر `customers:orders:view` |
| المطالبات | عرض/متابعة فقط (لا حسم) | عرض + **حسم** (`warehouse:claims:resolve`) | عرض + **حسم** (غير المُقدِّم) | — |
| أرضية التشغيل | ✅ عدسة كاملة | ✅ عدسة كاملة | ❌ (لا يخصه) — لا مدخل في WAREHOUSE_NAV | ❌ |
| المنتج التام | قراءة الحالة | قراءة + استلام | ✅ استلام (`warehouse:finished_goods:receive`) | — |
| التقارير | ✅ | ✅ | — | لاحقًا (T6) |
| إغلاق الأمر | ✅ (`production:orders:close`) | ✅ | ❌ | ❌ |

**قاعدة الحاكمية:** إظهار الإجراء = صلاحية (`hasPermission`) + حالة الأمر + فصل المسؤوليات (`dispatchedByMe`/من سجل المرتجع سابقًا) — نفس القواعد الثلاثية الحالية، والخادم هو حكم النهائي. لا يُخفى زر إلا بصفته مجرد إخفاء؛ كل نقطة نهاية تبقى محمية خادميًا كما هي.

## القسم 3 — مصفوفة Internal vs. CMT (ما يظهر وما يختفي في كل تبويب)

**المصادر الديناميكية المتاحة في النموذج (بدون Backend جديد):** `order.manufacturing_type` (`internal`/`external`)، `order.customer_name`، `materials[].supplied_by` (`customer`/`factory`)، `materials[].commercial_treatment`، `order.allowed_waste_pct`، `order.excess_waste_qty/_cost`، حصص `ProductionOrderDemand` (أوامر مجمعة)، وملكية البنود (`product_type`).

| التبويب | 🏭 تصنيع داخلي (Internal) | 🧵 تشغيل للغير (CMT) |
|---|---|---|
| **1. نظرة عامة** | لافتة «الخامات والمنتج التام ملك المصنع» + بطاقة **تخصيصات عملاء الأمر** (حصص/نسب/استيفاء) للأوامر المجمعة | لافتة «خامات العميل أمانة — سقف هالك {allowed_waste_pct}» + بطاقة بيانات العميل ومرجع اتفاق التشغيل؛ **لا تخصيصات طلبات** (أمر العميل واحد معروف) |
| **2. الخامات** | أعمدة المصدر (مستلزمات/يدوي)، الصرف من مخزن خامات المصنع، عيوب الاستلام العادية + مطالبات العجز T2 | شريط «ملكية العميل» على كل سطر (`supplied_by=customer`)، التركيز على **سندات أمانة**، مطالبات العجز مع كون الخامة ملك العميل، وعمود المعاملة التجارية بارز |
| **3. التنفيذ والإنتاج** | كما هو (المراحل الخمس + العيوب) — المصنع يدير خطه | نفس المراحل لكن أجور التشغيل هي منتجنا (CMT fee)؛ تلميح في العيوب: الإصلاح على حساب المصنع إن تجاوز السبب نطاق أمانة العميل (عرضي فقط) |
| **4. المنتج التام** | استلام إلى مخزن تام **المصنع** + توزيع الحصص على طلبات العملاء | استلام إلى مخزن تام **العميل** (رصيد مالكه)؛ لا توزيع حصص؛ تمييز «تصنيع خاص: العميل» |
| **5. التسوية** | تسوية رصيد الورشة إلى صفر (مستهلك/مرتجع/تالف) + مرتجعات داخلية | **تسوية أمانة العميل**: مصير كل خامة (مستهلك للإنتاج/هالك مقابل السقف/متبقي يُرجع) + مقارنة `excess_waste_qty` بالسقف {1.5% أو قيمة الأمر} + مرتجع للعميل بحالة الفحص + إبراز أي تجاوز هالك قبل الإغلاق |
| **6. الإغلاق** | مراجعة: مراحل مكتملة، رصيد صفر، مطالبات محسومة، عجز إنتاجي موثق + تكاليف المصنع النهائية | كل ما سبق **+ بوابة تسوية أمانة العميل**: لا إغلاق قبل توثيق مصير خامات العميل كاملة وإقرار تجاوز الهالك إن وُجد + مصنعية التشغيل (الأجر) مرئية |

**قواعد العرض:** القاعدة ليست «إخفاء» بل **إعادة ترتيب الأولوية** — CMT يرفع أمانة العميل والهالك والتسوية إلى المقدمة؛ Internal يرفع التخصيصات وتكاليف المصنع. كل ما يظهر في النمطين مدعوم بالبيانات الموجودة اليوم؛ ما هو غير مدعوم يُوثَّق أدناه ولا يُبنى بيانات خيالية له.

## القسم 4 — خطة الترحيل الآمن لـ T4.2 (Safe Migration Plan)

## ملخص تنفيذي

- **الوضع:** تفاصيل أمر التشغيل = Modal واحد 2,248 سطرًا بـ7 تبويبات و19 استدعاء API و10 صلاحيات — كل مكتسبات T1–T3 مثبتة داخله أو بجواره وتعمل.
- **الحل:** تفكيك إلى 8 أقسام ملفية ثم تركيبها في `OrderDetailsPage` بـ6 تبويبات حسب دورة الحياة، مع طبقة تحويل تبويبات تحفظ عقد `OrderDetailTab/NavFocus` وصندوق المهام حرفيًا؛ مساحة الإنتاج تتوسع إلى 6 مسارات (2 جاهزة من T2/T3، 3 عدسات وبوابات بدون Backend، 1 مؤجلة لـT6).
- **الديناميكية:** Internal vs CMT عبر بيانات موجودة (`manufacturing_type`, `supplied_by`, `allowed_waste_pct`, `excess_waste_qty`, `demands`) — إعادة ترتيب أولويات العرض، لا منطق أعمال جديد.
- **الترحيل:** 5 مراحل (M0–M4) كل منها صغيرة وقابلة للإرجاع وببوابة اختبارات، مع 5 حواجز صلبة تحمي T1–T3.
- **فجوات خادمية:** 9 ملاحظات موثقة (G1–G9) — أغلبها اختياري أو مؤجل؛ لا يوجد أي منها مانع لتنفيذ T4.2 بالكود الحالي.

**بانتظار اعتماد:** D-4.1a (موضع التكاليف)، D-4.1b (عرض مطالبات العجز في الخامات)، D-4.1c (الصفحة داخل مسار `batches`)، وشكل مساحتي «أرضية التشغيل» و«المنتج التام» (تبويبات داخل الـHub أم مساحتان مستقلتان).
